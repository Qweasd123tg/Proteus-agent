# Замысел Proteus

Уточнён владельцем 2026-10-02.

## Для Чего Нужен Конструктор

Proteus нужен как модульная среда исполнения агентных систем для разных
предметных областей. Владелец должен иметь возможность увидеть новый алгоритм,
написать узкий модуль и включить его в свою сборку. Чат, разработка кода,
обработка данных и работа по событиям — возможные назначения таких сборок.
Наличие диалога, языковой модели или coding tools определяется задачей сборки.
Рабочие сборки показывают полезность конструктора на реальных задачах.

Ценность Proteus — небольшой радиус изменений при замене поведения:

```text
идея -> module implementation -> выбор в profile -> проверка результата
```

Собственные алгоритмы и сочетания понравившихся частей разных агентов —
обычное назначение платформы. Например, можно совместить отдельные решения
Codex и OpenCode в своём профиле.

## Архитектурный Принцип

```text
Core -> Contract -> Module Implementation

authority(module) = authority(slot, invocation_context)
```

Core отвечает за сборку агента, разрешённые операции, запуск и остановку
модулей. Агент собирается из модулей, подключённых к слотам. Слот задаёт
контракт поведения и способ выбора реализации. Модуль — отдельная программа
со своим алгоритмом; она может реализовать один или несколько слотов.
Права определяются контрактом выбранного слота и условиями вызова.
Профиль связывает настройки и выбранные реализации.

### Долгосрочная Граница — Planned

Общее ядро исполнения владеет запуском компонентов, идентичностью и
маршрутизацией вызовов, снимком конфигурации, отменой, сроками выполнения,
допуском операций и записью фактов исполнения. Предметные контракты задают
входы, результаты, допустимые эффекты, композицию и правила состояния.
Конкретные алгоритмы и интерфейсы принадлежат модулям и сборкам.

Каталог сегодняшних слотов не является окончательным словарём платформы.
Цель — подключать новые предметные контракты и реализации без добавления их
алгоритмов в ядро. Сборка без диалога должна иметь естественный вход и результат,
без представления события как пользовательского сообщения. Conversation
history, turns и compaction принадлежат разговорному контракту.

Host допускает контракт и определяет права его реализации по контракту и
условиям вызова. Само объявление export модулем дополнительных прав не даёт.
Способ подключения новых семейств контрактов ещё требует отдельного решения;
универсальный механизм их регистрации пока не реализован. Границы и
контрольный сценарий описаны в
[execution-runtime.md](../architecture/execution-runtime.md).

### Действующая Сборка — Implemented

В текущем формате конфигурации `components.<id>` описывает запуск модуля,
а `exports.<slot>.<module_id>` — предоставляемые им реализации слотов.
Все они работают в одном процессе с общим жизненным циклом.

Основной пользовательский клиент — приложение. Его расширения интерфейса
используют публичный контракт агента; Core и модули работают без знания
конкретных экранов. Функции диагностики постепенно входят в это приложение
как расширения интерфейса.

Новая реализация существующего слота подключается через его контракт.
Новый слот нужен, когда появляется отдельная общая обязанность Core;
его правила описаны в
[slot-governance.md](../architecture/slot-governance.md).

Нельзя гарантировать, что любой будущий алгоритм поместится в сегодняшние
контракты. Если идея требует других общих правил, границу можно изменить.
Основанием служит конкретная потребность или дефект, включая собственные
идеи владельца. Реконструкция чужого агента для этого не обязательна.

Замена модуля не должна менять его разрешённые операции. Совместимость
поведения модулей проверяется отдельно: одинаковый протокол обмена
не гарантирует одинакового понимания истории и дополнительных данных.

## Первый Рабочий Пример

Первый выбранный пример — близкая реконструкция обычного сценария Codex.
Она помогает проверить каркас на уже известном полезном поведении.
Требования этой сборки не задают поведение всех агентов на Proteus.

Владелец должен пользоваться этой сборкой на Proteus и не замечать
существенной разницы. Проверки на задачах должны подтверждать совпадение
результатов и расхода. Полная копия всех мелких возможностей Codex не нужна.

Получившиеся модули и профили могут стать первыми примерами для сообщества.
Готовая удобная сборка допустима; её implementations имеют те же права, что
любые другие. Имя `codex` само по себе не доказывает совместимость.

Свои улучшения и смешанные profiles описывают отличия явно и сохраняют
отдельную идентичность от сборки, на которой проверяется совпадение с Codex.

## Что Подтверждает Полезность Каркаса

Нужны рабочая сборка для повседневных задач и возможность полезно заменить
её отдельную часть обычным модулем, без переписывания Core и потери корректности.
Для первой сборки это проверяется на примере Codex. Для собственных сочетаний
результат оценивается по их задаче, а не по совпадению с Codex.

Сегодняшние contracts не объявляются окончательным набором возможностей.
Новые идеи могут потребовать изменения границ. Универсальность проверяется
конкретными заменами и сценариями, а не обещанием заранее вместить любой агент.
Для долгосрочной границы нужен сценарий со структурированным входом и
результатом без чата и модели, с проверяемыми отменой, завершением и состоянием.

Точное текущее состояние — в [scope.md](scope.md), критерии результата —
в [roadmap.md](roadmap.md). Архитектурные правила и ограничения описаны
в профильных справочниках.
