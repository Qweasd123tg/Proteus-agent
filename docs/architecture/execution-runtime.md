# Исполнение Вне Чата

Proteus развивается через существующие слоты. Этот документ описывает задел
для задач вне чата, его ограничения и возможное развитие, когда конкретной
задаче станет тесно в текущих контрактах. Целевая граница и контрольный сценарий
ниже не требуют немедленной перестройки runtime. Текущий приоритет — в
[roadmap.md](../product/roadmap.md), замысел — в [spec.md](../product/spec.md),
действующая архитектура — в [architecture.md](architecture.md).

## Возможное Развитие — Planned

| Слой | Ответственность |
|---|---|
| Общее ядро исполнения | Допуск одного выполнения, захват согласованного снимка сборки, идентичность и маршрутизация вызовов через host, процессы, отмена, сроки выполнения и запись исхода |
| Предметный контракт | Типы входа, результата и событий; разрешённые операции; правила композиции, состояния, checkpoints, ошибок, восстановления и replay |
| Module implementation | Алгоритм обработки данных или управления поведением через допущенный контракт |
| Сборка и интерфейс | Выбор реализаций, связывание предусмотренных контрактом операций, источники входов и представление результата |

Conversation history, user/assistant messages, turns и compaction относятся
к разговорному контракту. Другие задачи могут иметь собственные данные и
состояние. Модель, поиск и инструменты подключаются по потребности сборки.
Рабочий каталог нужен операциям с файловой системой; его наличие не должно
быть условием любого входа в ядро.

Новый предметный контракт должен позволять менять реализации без знания
их алгоритмов в ядре. Способ допуска и подключения семейств контрактов
выбирается при таком переходе; универсальная регистрация пока не реализована.
Действующий каталог остаётся рабочей основой без гарантии, что он вместит
любую будущую задачу.

Для будущего контракта сохраняются требования действующих границ:

- Host определяет разрешённые методы, composition и protocol-visible
  `host.*` права вызова. Модуль не получает их самим объявлением export;
  `module_id`, язык и происхождение реализации не меняют эту authority.
- Вызовы между exports маршрутизирует host с явным invocation context.
  Protocol-visible права участников не объединяются на процесс или сборку.
- Используется общий process boundary; второй native extension path не нужен.
- Контракт определяет смысл данных и правила переходов. Совпадение JSON-схем
  проверяет форму, но не подтверждает заменяемость поведения.

Ядро обеспечивает проверяемый жизненный цикл вызова. Корректность предметного
состояния, допустимость результата и воспроизведение алгоритма подтверждаются
отдельно по контракту сборки. Process restart сам по себе не восстанавливает
вычисление и не доказывает однократность внешнего эффекта.

## Контрольный Сценарий

Сценарий для проверки этой границы: событие о готовом наборе числовых
измерений → вычисление агрегатов → запись структурированного результата.
Данные события имеют собственную идентичность и описываются предметным DTO;
текстовый prompt, модель и conversation history для вычисления не нужны.
Это пример проверки возможного перехода. Сценарий не выбран для реализации
на текущем этапе; готового профиля и установленного контракта нет.

1. Источник передаёт одно структурированное событие. Host проверяет контракт
   входа и допускает отдельное выполнение из одного снимка конфигурации.
2. Сборка выбирает точную реализацию процессора. Два независимых варианта —
   обработка набора целиком и последовательная агрегация — должны выполнять
   одну обязанность и возвращать результат с одинаковым смыслом.
3. Процессор принимает предметные данные и возвращает агрегаты, например
   количество, сумму и границы значений. Эти поля являются результатом,
   а не произвольным дополнением к обязательному assistant response.
4. Запись результата проходит через допущенную host операцию. Если используется
   существующий tool, сохраняется `ToolRegistry -> policy -> approval -> safety`
   path. В контрольном сценарии процессор запрашивает эффект у host; запись
   результата и решения policy входят в evidence этого пути.
5. Host фиксирует фактический исход выполнения и доступный результат.
   Отмена, срок выполнения и потеря процесса имеют явную семантику.
6. После перезапуска результат читается по идентичности выполнения.
   Повторная доставка события и незавершённая запись эффекта обрабатываются
   по явно выбранным правилам предметного контракта.

Этот сценарий проверяет вход и жизненный цикл одной операции. Источник входа
может быть локальным вызывающим кодом; наблюдение за файлами, таймеры и
долгоживущие потоки требуют собственных контрактов запуска и остановки.

## Что Есть Сейчас — Implemented

| Граница | Текущее поведение | Значение для контрольного сценария |
|---|---|---|
| Идентичность | [ExecutionScope](../../crates/proteus-contracts/src/contracts/execution.rs) содержит `ExecutionId` и cancellation без chat identity | Уже есть основа одного выполнения; `TurnId` и broker `InvocationRef` остаются отдельными identity |
| Component invocation | [Component Runtime v2 / wire v3](process-module-architecture.md) обслуживает persistent multi-export процессы, callbacks, deadlines, отмену и restart | Общий process lifecycle можно использовать; terminal одного вызова не является durable settlement всей задачи |
| Снимок и admission | [AgentRuntime](../../crates/proteus-core/src/core/runtime/execution.rs) захватывает snapshot и scope для Turn и typed операций `execute_tool` / `remember` | Механизм уже есть для этих входов; публичного входа произвольной предметной задачи пока нет |
| Самостоятельный Workflow | [WorkflowInvocationContext](../../crates/proteus-contracts/src/contracts/workflow/invocation.rs) имеет `Execution` без conversation; [registry](../../crates/proteus-core/src/core/registry.rs) создаёт такой context | Прямой вызов процессора без модели и диалога возможен; отдельный registry invocation не получает admission и settlement произвольной операции от `AgentRuntime` |
| Вход и результат | [AgentTask](../../crates/proteus-contracts/src/domain/task.rs) требует текст и `cwd`; [WorkflowOutput](../../crates/proteus-contracts/src/contracts/workflow.rs) содержит `AgentOutput`, messages и compactions | Событие можно закодировать текстом и результат положить в metadata, но естественный типизированный предметный вход и результат отсутствуют |
| Разрешённые действия | [WorkflowHostRuntime](../../crates/proteus-core/src/core/workflow_host.rs) исполняет detached tools через `BoundTools` | Общий policy/approval/safety path уже применяется без чата |
| События и checkpoint | [EventEnvelope](../../crates/proteus-contracts/src/domain/events.rs) требует session/thread; `host.events.emit`, history checkpoint и compaction требуют `Agent` context | Для standalone вычисления отсутствуют предметный progress stream и checkpoint состояния |
| Journal и завершение | [Execution attribution](canonical-turn-data.md#текущий-execution-owner) допускает detached model/tool facts; `TurnSettled` относится к chat lifecycle | Запись отдельных effects не даёт общего durable `ExecutionSettled` и cold result произвольной задачи |
| Replay | [Workflow replay](../../crates/proteus-core/src/core/workflow_replay/mod.rs) восстанавливает conversational context из записанного Turn | Model-free Turn поддержан, но самостоятельный предметный алгоритм не получает автоматически checkpoint/replay |
| Каталог контрактов | [ModuleKind](../../crates/proteus-contracts/src/domain/module_manifest.rs), [authority table](../../crates/proteus-module-protocol/src/authority.rs), config и adapters задают host-defined набор | Новое семейство контрактов пока требует согласованного изменения этих границ |

Ненастроенная модель действительно отсутствует. Другие невыбранные services
получают текущие `Null`/`No*`/empty реализации в registry. Это поведение сборки
не означает, что обработчик данных обязан использовать поиск, память,
compactor или AgentControl.

Публичный `AgentRuntime::run` принимает строку и открывает Turn с user message.
Текстовый обход через `AgentTask.text` позволяет экспериментировать с обработкой
данных, но сохраняет разговорный envelope и не закрывает пробел верхнего
admission, состояния и завершения.

Существующие evidence targets:

- [standalone_workflow_assembles_and_runs_without_model_or_conversation](../../crates/proteus-core/tests/execution_boundary/workflow.rs)
  вызывает реальный процессный Workflow через assembly/registry без модели и
  conversation, с пустой history. Он проверяет контракт вызова, а не вход
  структурированной задачи через `AgentRuntime`.
- [execution_boundary](../../crates/proteus-core/tests/execution_boundary.rs)
  проверяет detached tools и memory, admission и recording без Turn.
- [project_check_workflow](../../modules/reference/process-module/tests/project_check_workflow.rs)
  проверяет детерминированный controller и replay без model call на success
  path, но его верхний жизненный цикл по-прежнему является Turn.

## Проверка Возможного Перехода — Planned

Если конкретная задача потребует целевой границы, минимальная проверка —
типизированная операция вне диалога с собственными admission, результатом
и записью завершения. Она переиспользует `ExecutionScope`, согласованный
snapshot, process invocation и существующие
effect paths; разговорный Turn должен использовать общее исполнение через свой
adapter.
Точные DTO, владелец storage и способ допуска предметного контракта требуют
решения перед изменением runtime.

Критерии проверки:

- Вход и результат проверяются по предметному контракту; нет фиктивного user
  message или обязательного model call.
- Две независимые реализации выбираются через сборку и проходят один process
  contract с одинаковыми protocol-visible правами.
- Проверены успешный результат, неверный input, ошибка модуля, отмена,
  истечение срока и потеря component. Исход invocation и всей операции
  различаются явно.
- Зафиксированный результат доступен при cold read; потеря процесса не
  превращает неподтверждённый эффект в успех. Правило повторной доставки
  определено до реализации; неизвестный эффект не повторяется молча.
- Предметный replay использует записанные входы и outcomes в объявленной
  границе и не исполняет реальный уже записанный внешний эффект заново.

Проверки существующего `module_swap` и разговорного journal/replay сохраняют
свою роль при изменении общей границы. Новый предметный сценарий дополняет их
отдельным источником дефекта: отсутствием разговора и собственной семантикой
состояния. Применимые gates выбираются по
[матрице тестирования](../development/testing.md#evidence-matrix).
