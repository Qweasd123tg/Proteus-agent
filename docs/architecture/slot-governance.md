# Когда добавлять новый слот

Слот — это контракт поведения и место, где система выбирает его реализацию.
Модуль — запускаемый процесс, который может реализовать один или несколько
слотов. Слот сам по себе не является отдельным процессом. Новый слот нужен
для класса заменяемого поведения, а не для каждой новой функции или идеи из
другого агента.

Здесь описаны правила действующего host-defined каталога слотов. Его набор
остаётся рабочей основой и может развиваться по конкретным потребностям.
Универсальная регистрация контрактов не является задачей текущего этапа;
задел и возможная граница описаны в
[execution-runtime.md](execution-runtime.md). Новый слот проходит правила ниже,
а модуль не может объявлением export создать новый host callback или права.

При изменении слота conversation identity, history и модель требуются только
там, где они нужны по смыслу операции. Общие identity, отмена и process lifecycle
сохраняют независимость от чата; разговорные операции явно требуют свой context.

Требование к поведению само по себе не означает новый слот. Иногда достаточно
существующего инструмента, шага `Workflow`, сервиса приложения или уже
определённого контракта. Поэтому здесь не нужен отдельный реестр возможностей,
универсальный `Capability` enum, поиск сервисов по строковому имени или
механизм, через который модуль объявляет новые возможности при подключении.

Для обычного поведения система выбирает одну реализацию. Если несколько
обработчиков должны работать вместе, контракт заранее задаёт их порядок:

```text
composition(contract) = select_one | ordered_many
```

`ordered_many` допустим только для явно описанной цепочки с типизированными
данными и одинаковыми разрешёнными действиями у всех участников. Это не способ
объявлять новые слоты строками или собирать произвольные обработчики.

Список слотов задаёт система. `SlotId` унифицирует ключи каталога уже
известных слотов ядра. При этом `ModuleKind`, схема настроек, создание
типизированных реализаций и таблица
разрешённых действий остаются явно определёнными. Поэтому новый слот требует
согласованных изменений в `proteus-contracts`, протоколе обмена с процессом,
подключении и настройках ядра, а также проверок границы.

У нового слота сразу должен быть общий контракт обмена с процессом. Второй
путь подключения через нативные расширения запрещён. Для всех реализаций слота:

```text
authority(module) = authority(slot, invocation_context)
```

Реализации одного слота должны получать одинаковые разрешённые методы системы,
настройки и правила отмены, ошибок и жизненного цикла. Эти правила не должны
зависеть от `module_id`.

После выбора места для поведения проверяйте изменение по
[стандарту тестирования](../development/testing.md#стандарт-изменения).
Этот документ помогает выбрать контракт; руководство по тестированию объясняет,
как проверить поведение, заменяемость и восстановление после повторного
подключения.

Например, идеи Cursor для динамического контекста, Codex для поиска
инструментов или Claude для маршрутизации подзадач сначала сопоставляют с
существующими контрактами контекста, показа инструментов, `Workflow`,
подтверждений, памяти, сжатия истории, хранения и `Model`.

## Условия для нового слота

Новый слот можно добавить, только если выполнены все условия:

1. Есть хотя бы две работающие независимые реализации с разными алгоритмами
   или источниками данных. Запланированный вариант, пустая реализация и
   транспортная обёртка той же реализации не считаются.
2. Поведение нельзя выразить через существующие `Tool`, `Workflow`,
   `ContextBuilder`, `ToolExposure`, `SearchBackend`, `MemoryStore`,
   `ApprovalPolicy`, `PatchApplier`, `Compactor` или `Model`.
3. Ядро должно само вызывать это поведение в устойчивой точке жизненного цикла.
   Если достаточно инструмента, шага `Workflow` или `context_provider`, новый
   слот не нужен.
4. Данные контракта можно описать типами DTO без типов конкретного интерфейса,
   провайдера, продукта или реализации.
5. Слот не заставляет среду исполнения знать алгоритм конкретного модуля или поведение
   конкретного продукта либо внешнего агента.
6. Проверки границы и замены реализации могут подтвердить, что обе реализации
   работают через один контракт.

Для `ordered_many` дополнительно нужны:

1. Хотя бы два независимо полезных обработчика, которые должны работать
   одновременно, а не выступать альтернативами.
2. Устойчивый контракт входа и выхода либо уведомления с типизированными
   данными, без доступа к конкретным объектам ядра или интерфейса.
3. Явный порядок из снимка конфигурации, правило разрешения конфликтов и
   повторная проверка данных после каждого изменения.
4. Срок выполнения и отмена для каждого обработчика, а также заранее
   определённое поведение при его ошибке: продолжать или прерывать цепочку.
5. Правила работы обработчиков с состоянием при ответвлении, перезагрузке и
   перезапуске.
6. Проверки порядка `A -> B` и `B -> A`, ошибки одного обработчика и одинаковых
   прав независимо от `module_id`.

Широкий `ExtensionAPI`, объединяющий инструменты, внутренние данные провайдера,
состояние интерфейса и изменение сессии, не добавляют ради удобства. Сначала нужно
убедиться, что это один контракт, а не объединение прав разных слотов.

Если хотя бы одно условие не выполнено, идею развивают в существующем модуле,
исследовательском модуле или документации будущей работы.

## Куда относится поведение

| Требуется | Существующее место |
|---|---|
| Модель сама вызывает действие | `Tool` |
| Меняется порядок действий агента | `Workflow` |
| Контекст добавляется или сокращается перед вызовом модели | `ContextBuilder`, `context_provider` или `Compactor` |
| Выбирается, какие инструменты показать модели | `ToolExposure` |
| Ищутся данные в проекте | `SearchBackend` или источник данных внутри `ContextBuilder` |
| Долговременная память явно сохраняется или читается | `MemoryStore` вместе с `Tool` или `Workflow`; фоновая работа остаётся исследованием до появления двух реализаций |
| Принимается решение `allow` / `ask` / `deny` | `ApprovalPolicy` и передача решения на подтверждение |
| Применяется изменение файла | `PatchApplier` или `Tool` поверх него |
| Меняется запрос к провайдеру, поток ответа или учёт использования | `Model` и его контракт обмена с процессом |
| Показывается отладочная информация или меняется интерфейс | протокол сервера приложения или клиент UI/CLI |
| Несколько независимых обработчиков последовательно меняют один DTO | Возможный контракт `ordered_many`; сначала нужны два одновременных применения и правила цепочки |

## Несколько идей в одной сборке

Если внешняя архитектура состоит из нескольких идей, их можно собрать
конфигурацией и профилем из существующих модулей. Такой набор не становится
одним новым слотом.

В этом репозитории `pack` означает:

```text
pack = конфигурация и профиль + набор реализаций модулей + документация и проверки
```

`pack` позволяет проверить совместную работу существующих слотов. Он не
получает особых прав в ядре и сам по себе не задаёт стабильный ABI.

Пример профиля с условными `module_id`:

```text
пример профиля
  workflow       = "coding.plan_execute_review"
  context        = "repo_aware"
  search         = "path_fuzzy"
  policy         = "exec_rules"
  patch          = "verified"
  tool_exposure  = "deferred_tools"
```

Профиль может сочетать проверенные решения из других агентов. Каждая
реализация остаётся заменяемой и проверяется отдельно. Названия продуктов,
например `codex` или `opencode`, допустимы в именах профилей и реализаций,
но не дают дополнительных прав. Слот называют по его задаче. Если профиль
заявляет совместимость, её подтверждают проверками в явно указанной границе.

## Исследовательский модуль

Если идея перспективна, но контракт ещё не определён, её можно оставить в
`modules/research`:

- модуль не включают в рабочий профиль по умолчанию;
- в README указывают, какого общего контракта не хватает;
- код остаётся черновиком и не подключается к рабочей конфигурации;
- в документации не называют его устойчивым API слота;
- до принятия нового слота нужен второй независимый случай применения.

`modules/research/tool-output-artifacts` — такой черновик. Он исследует идею
артефактов вывода инструмента из Cursor, но сам по себе не доказывает
необходимость публичного контракта обмена с процессом.

## Что не добавлять

- Слоты с именем продукта: `cursor_context`, `codex_tool_search`,
  `claude_subagent`.
- Слоты только для передачи состояния интерфейса в ядро или только для одного модуля.
- Контракты с типами запросов или ответов конкретного провайдера.
- Контракты, из-за которых ядро знает внутренние шаги модуля.
- Цепочки `ordered_many` без порядка, закреплённого снимком конфигурации.
- Общий контракт расширений, который даёт инструменту дополнительные права
  только из-за способа регистрации.
- Запасные пути для старых экспериментальных форматов без отдельного решения
  владельца с явно указанной границей совместимости.

## Что требуется перед объединением изменений

- Описание DTO и trait в `proteus-contracts`.
- Один протокол обмена с процессом с одинаковыми разрешёнными действиями для всех
  реализаций.
- Явное правило, обязателен ли слот, без особого пустого или фиктивного модуля.
- Ключ конфигурации и пример выбора реализации.
- Проверка соответствия протоколу, границы и замены модуля.
- Обновление `docs/architecture/modules.md`,
  `docs/architecture/process-module-architecture.md` и, если затронута
  конфигурация, `docs/guides/configuration.md`.
- Хотя бы две работающие независимые реализации; пустая, старая под другим
  именем и лишь запланированная не считаются. Проверка замены должна вызвать
  обе реализации через один путь среды исполнения.

## Упорядоченные обработчики `hook/v2`

`hook/v2` обслуживает несколько одновременно включённых обработчиков в общих
точках перед вызовом модели или инструмента и после выполнения инструмента.
Эти точки принадлежат системе, поэтому обработчик не приходится добавлять в
каждый `Workflow`. Работающие реализации, включаемые явно, — добавление
инструкций и ограничение размера вывода инструмента. Контракт ограничивает
изменения данных и не открывает произвольные обратные вызовы.

`modules.hooks` задаёт точный порядок. У каждого обработчика одинаковые
разрешённые действия, свой срок выполнения, правила отмены и проверка
результата. Ошибка перед моделью или инструментом прерывает цепочку. После
инструмента сохраняется фактический результат действия вместе с явной ошибкой.
Уведомления о жизненном цикле отправляются по мере возможности. Состояние
обработчика не обязано восстанавливаться после перезапуска. Проверки цепочки
охватывают `A -> B`, `B -> A`, ошибку и запрет обратных вызовов к системе.

Тот же `hook/v2` включает обработку аргументов перед инструментом и проверку
завершения хода; новых прав и обратных вызовов нет. После каждого экспорта
аргументы проходят общую проверку до политики и подтверждения. `Requested` сохраняет
происхождение запроса от модели. Обработчик перед завершением может вернуть
только причину ограниченного продолжения, но не изменить задачу, историю или вывод.
Корневой агент задаёт лимит 8, общий срок выполнения, контрольную точку и решение о
финальном ответе. Проверки замены и исполнения обработчиков охватывают реальный
вызов и повтор, границу лимита, сохранение ответа-кандидата при отмене или
истечении времени и единственный принятый финал в интерфейсе.
