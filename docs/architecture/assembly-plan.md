# План Сборки Агента

`AssemblyPlan` описывает, какие реализации слотов и настройки выбраны
конфигурацией до запуска модулей:

```text
AppConfig + ModuleCatalog
          |
          v
     AssemblyPlan       без запуска процессов модулей
          |
          v
   проверка контрактов
          |
          v
    RuntimeRegistry
          |
          v
     AgentRuntime
```

Это описание сборки для Core. Оно фиксирует подключение к существующим
контрактам, сохраняя принцип `Core -> Contract -> Module Implementation`.

## Зачем Он Нужен

Запуск агента, `doctor`, просмотр схемы и обновление конфигурации используют
один план. Выбор реализаций определяется в одном месте, поэтому эти команды
не расходятся из-за повторного разбора `AppConfig`.

План содержит:

- выбранную модель и её реализацию;
- основные слоты и точный `module_id` каждого выбора, отдельно от
  поставщиков контекста и списка инструментов;
- источник реализации и `component_id` записи запуска её процесса;
- запускаемые модули, предоставляемые ими реализации слотов, версии
  контрактов и методы Core, которые они могут вызывать;
- запрошенные и настроенные инструменты, серверы MCP и возможности
  управления другими агентами;
- предупреждения и ошибки проверки конфигурации.

Неизвестная выбранная реализация или повтор имени в `tools.enabled`
блокирует сборку до создания `RuntimeRegistry` и запуска процессов модулей.

## Сборка И Обновление Конфигурации

`PreparedAssembly` объединяет проверенный `AssemblyPlan` и созданный из него
`RuntimeRegistry`. Core принимает их только вместе. При обновлении новая пара
сначала полностью собирается, затем одним действием заменяет текущую сборку
`RuntimeSnapshot` и увеличивает её номер `ModuleEpoch`.

Уже начатый ход использует прежнюю сборку. Следующий ход получает новый план
вместе с соответствующими реализациями модулей. План и подключённые модули
не могут относиться к разным версиям конфигурации.

## Просмотр

Человекочитаемый вариант:

```bash
proteus --config codex inspect plan
```

Полное описание в JSON:

```bash
proteus --config codex inspect plan --format json
```

У запущенного сервера текущий план доступен через:

```text
GET /inspect/plan
```

`inspect plan` не запускает процессы модулей и не проверяет их ответы на
начальный запрос. Он показывает запрошенные инструменты. Фактически
зарегистрированные инструменты после сборки показывает `inspect topology`.

## Что Не Попадает В JSON

JSON плана предназначен для просмотра. Он не является вторым форматом
конфигурации: в него не записываются исходный `AppConfig`, `module_config`,
секреты поставщика модели, аргументы запуска и значения переменных окружения.
Этот JSON нельзя загрузить обратно вместо обычной проверки конфигурации
и контрактов.

## Границы Гарантии

- Разрешённые по протоколу операции определяются контрактом слота, а не
  значением `module_id`.
- Процессы модулей работают с правами владельца. План сборки не добавляет
  ограничений доступа к операционной системе.
- Доступный модели список инструментов может меняться во время вызова
  из-за проверки разрешений и `ToolExposure`. Статический план не подменяет
  эту проверку.
- План фиксирует `agent_control.surface`, но не превращает `AgentControl`
  в слот модуля и не записывает описания профилей ролей. Запущенные экземпляры
  Proteus относятся к состоянию конкретной сессии и в план не входят;
  см. [subagents.md](subagents.md).
- Настройки модели, рассуждения и разрешений для конкретного запуска
  не переписывают план текущего `ModuleEpoch`. Их действующие значения
  отдельно возвращают `/config` и схема агента.
- Обновление всей сборки произвольным способом не поддерживается. Сейчас
  описанный порядок используется при начальной сборке, сохранении через
  конструктор конфигурации и поддержанном обновлении инструментов.
